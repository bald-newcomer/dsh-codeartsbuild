## 0. 文档定位

回答「创建构建任务时仓库来源的两条链路怎么打通」：
1. **本地仓库方案**（已拉取到本地的仓库）——探索 CodeArtsRepo 接口，打通「获取上传凭证 → 本地提交到 CodeArtsRepo → 基于 repo 信息初始化 scm → createJob」

## 1. CodeArtsRepo 接口探索结论（2026-09-23 实测）

### 1.1 服务定位

**CodeArtsRepo（代码托管）＝ CodeHub 的新品牌名**——`scm_type=codehub` 对应的代码托管服务。它是**独立 OpenAPI 服务**（`api-codeartsrepo`），与 CodeArtsBuild（`cloudbuild-ext`）不同服务、不同网关、不同 SDK（`huaweicloud-sdk-codeartsrepo`）。

### 1.2 Endpoint（文档确认）

代码托管服务终端节点（华北-北京四 cn-north-4）：

```
https://codehub-ext.cn-north-4.myhuaweicloud.com
```

（其他区域同构：`codehub-ext.{region}.myhuaweicloud.com`；个别区域为 `codeartsrepo-ext.{region}`）

### 1.3 认证方式与接口实测（2026-09-23 ✅ 已确认：AK/SK 可行，接口已调通）

## 2. 本地仓库方案（#20）

### 2.1 链路设计（接口已全部实测确认）

```
本地 git 仓库（repoPath，已拉取到本地）
  ├─ ① 检测：git 仓？有无 remote -v？
  │    ├─ 已有 codehub 远端 → 走远端流程（§3）
  │    └─ 无远端 / 纯本地 →
  ├─ ② CodeArtsRepo 创建空仓：POST /v1/repositories { project_uuid, name }
  │    → 返回 repository_uuid
  ├─ ③ 回读仓库信息：GET /v1/repositories/{repository_uuid}
  │    → RepoInfo: repoId, name, sshUrl, httpUrl, webUrl, groupName, projectId
  ├─ ④ git push 凭证：
  │    ├─ SSH 方式：GET /v1/users/sshkey → 获取已注册 SSH 公钥（确认本地有对应私钥）
  │    └─ HTTPS 方式：用户在控制台配置 HTTPS 密码（API 未暴露），git push 时交互输入
  ├─ ⑤ git remote add origin <sshUrl 或 httpUrl> && git push -u origin master
  ├─ ⑥ 初始化 create_job.scms（按 §1.5 映射：scm_type=codehub, repo_id=repoId, url=httpUrl, web_url=webUrl）
  └─ ⑦ repo_build 本地验证 → create_job → run_job → wait_build → list_artifacts
```

## 5. 推送能力形态决策（#31，2026-09-23 定案）

### 决策：**独立工具 `repo_push`**（非 repo_build 内置 ensure_remote）

**理由**：

| 维度 | 独立工具 `repo_push` | repo_build 内置 `ensure_remote` |
|------|----------------------|-------------------------------|
| 职责单一 | ✅ 仓库推送与构建分离 | ❌ repo_build 承担构建+推送双重职责 |
| 可复用 | ✅ 用户可能只推送不构建（如仅建仓测试） | ❌ 推送绑定构建流程 |
| 可测试 | ✅ 独立单测（mock CodeArtsRepo API） | ❌ 与构建耦合 |
| 工具清单 | 新增 1 个工具（17→18 个） | 不新增工具，repo_build 扩展 |
| LLM 编排 | 模型按需调用（推送场景才调） | repo_build 内部隐藏调用（模型不可控） |

**设计**：新增工具 `codeartsbuild_repo_push`（17→18 个工具），职责：
- 入参：`repoPath`（本地仓库路径）、`projectUuid`（目标项目）、`repoName?`（仓库名，默认取目录名）、`branch?`（分支，默认 master）
- 流程：
  1. 检测本地 git 仓库（`git remote -v`）——已有 codehub 远端 → 返回已有仓库信息（跳过创建）
  2. 无远端 → `POST /v1/repositories { project_uuid, name }`（service=codeartsrepo）创建仓库
  3. `GET /v1/repositories/{repository_uuid}` 回读 RepoInfo（repoId/httpUrl/sshUrl/webUrl）
  4. 返回 RepoInfo + `remote_url` + `push_guidance`
  5. **实际 git push 由模型用宿主命令工具（bash/pwsh）自探索执行**（见 §7 形态调整，2026-09-28）
- 输出：`{ repository_uuid, repo_id, repo_name, url, web_url, ssh_url, branch, remote_url, push_guidance }`

> **实现状态（2026-09-23 ✅ 已实现并通过端到端验证）**：契约 `docs/api/tools/repo_push.md`、handler `src/providers/codeartsbuild/repo-push.ts`、6 单测、SKILL 编排已落地。见 §6 实测记录。
>
> **形态调整（2026-09-28，本文件同步更新）**：工具改名 `codeartsbuild_repo_prepare`（`src/providers/codeartsbuild/repo-prepare.ts`、契约 `docs/api/tools/repo_prepare.md`），**移除工具内 git push 固定逻辑**（pushWithToken/pushWithSsh/tokenUrl/CAB_REPO_TOKEN）；推送改由模型用宿主命令工具自行执行。详见 §7。

## 7. 形态调整：repo_push → repo_prepare（2026-09-28 定案）

> **2026-10-10 再演进（形态 B：恢复独立推送工具，内置一次智能尝试）**：`docs/example/session.jsonl` 实测证明"模型自探索 push"仍三连败（origin 跨项目误推 / SSL 自签名 / Git for Windows CreateFileMapping 崩溃）。决策：新增 `codeartsbuild_repo_push`（§2.18）——工具内置一次智能尝试（自动携带代理+SSL、push 前 origin 项目归属预检、失败 stderr 分类输出 next_actions）；SSL/NETWORK 自动重试一次，AUTH/RUNTIME_CRASH 交模型/用户接管。**repo_prepare 保留**（建仓需 AK/SK + codeartsrepo 网关），推送职责移交 repo_push。详见 §8。

### 背景

FE-08 §6 实测暴露：**本地 git push 受用户侧环境（认证/代理/网络）制约极大**——SSH 22 端口不通、HTTPS 需 GCM 交互认证、代理未配置即连接失败。固定 push 脚本无法穷举这些环境差异，失败诊断也只能靠 stderr 文本猜测，维护成本高、容错粗糙。

### 决策

**`repo_push` 瘦身改名 `repo_prepare`：建仓 + 回读 RepoInfo 保留在工具内（模型无法自建仓——需 AK/SK 签名 + service=codeartsrepo 网关），实际 git push 由模型用宿主命令工具（bash/pwsh）自探索执行。**

| 维度 | 原 repo_push（固定脚本 push） | 新 repo_prepare（LLM 自探索 push） |
|------|------------------------------|-----------------------------------|
| 建仓 + RepoInfo | 工具内置 | 工具内置（保留） |
| git push 执行 | 工具内置（HTTPS token / SSH fallback） | **模型用宿主 bash/pwsh 执行** |
| 认证/代理/网络诊断 | stderr 正则猜测 + 双通道 fallback | **模型读 stderr 自行分类决策**（认证→提示 token/SSH 密钥；网络→提示代理/网络） |
| 失败处理 | pushed:false + 指引 | push 失败不阻断，模型继续用 RepoInfo 建任务 + 附处理建议 |
| 重试 | 无明确上限 | 对齐强制规约 #6：3 轮升级用户 |

**依据**：dsh 宿主（standard agent preset）为模型装配了通用命令工具 `bash`（非 Windows）/`pwsh`（Windows）——模型本就有执行 git 的通道；`repo_build` 也验证了工具内 shell 执行模式。故 push 的执行与诊断交给模型，比固定脚本更适应本地环境差异。

## 8. 形态再演进：repo_prepare → repo_push（2026-10-10 形态 B 定案）

### 背景

`docs/example/session.jsonl`（2026-10-09 实跑）暴露：本地仓库 `D:\code\ai\dsh-quant` 创建构建任务时，模型按 §7 的"自探索 push"路径执行 git push **三连败**：

| # | 失败 | stderr 特征 | 根因 |
|---|------|-------------|------|
| 1 | origin 跨项目误推 | 本地 origin 指向项目 `624d3c36...`，repo_prepare 建仓于另一项目后模型仍对旧远端操作 | 模型忽略 `project_mismatch` 警告字段（机制层仅警告不阻断） |
| 2 | SSL 证书失败 | `SSL certificate OpenSSL verify result: self-signed certificate in certificate chain (19)` | 模型未携带 `-c http.sslVerify=false`（内网自签） |
| 3 | Git for Windows 崩溃 | `CreateFileMapping S-1-5-21... Win32 error 5. Terminating` | 宿主 Git 环境崩溃，模型不可预测 |

结论：**模型自探索 push 不可靠**——纯 SKILL 决策树（§7 形态）无法机制兜底。

### 决策（形态 B：独立工具内置一次智能尝试）

| 维度 | §7 repo_prepare（LLM 自探索 push） | 新形态 B repo_push（2026-10-10） |
|------|-----------------------------------|----------------------------------|
| 建仓 + RepoInfo | 工具内置 | repo_prepare 保留（不变） |
| git push 执行 | 模型用宿主 bash/pwsh 自探索 | **工具内置**：自动携带 `-c http.proxy` + `-c http.sslVerify=false` 推送 |
| origin 跨项目 | `project_mismatch` 警告（模型曾忽略） | **push 前 `git remote -v` 预检，机制阻断**（≠ projectUuid 不推送） |
| SSL/代理 | 模型读 stderr 自行处理 | **工具自动重试一次** |
| 凭据交互 | 模型提示用户 | 工具分类 `AUTH` 后交模型/用户（不代执行 GCM/访问令牌——2026-09-23 实测 HTTPS 需 GCM 交互，非交互 spawn 必败） |
| Windows 崩溃 | 模型盲撞 | 工具分类 `RUNTIME_CRASH` 如实上报，止住盲撞 |
| 失败输出 | 模型自行诊断 | `error_type` + `next_actions[]` 结构化输出 |

**机制兜底覆盖**：origin 跨项目（第 1 败）✅ 机制阻断；SSL/代理（第 2 败）✅ 自动重试；凭据与崩溃（第 3 败）⚠️ 如实分类上报交模型/用户，不伪装成功。

### 边界与风险

- **凭据交互**：repo_push 不代执行 GCM/访问令牌——`AUTH` 分类后交模型/用户配置（对齐 2026-09-23 实测）；**AK/SK 禁止当 push 凭据**（SKILL 规约 #9）。
- **Windows 崩溃**：工具不预测，价值在如实分类上报 + 止住模型空转；根本解决依赖宿主环境（升级 git），走 `next_actions → 升级用户`。
- **origin 跨项目**：push 前预检机制消除误推；用户本意切换项目须"刷新会话 projectId + 重新 repo_prepare"。
- **repo_prepare 保留**：建仓需 AK/SK + codeartsrepo 网关，模型无法自建仓，保留在工具内；push 职责移交 repo_push，职责不重叠。
