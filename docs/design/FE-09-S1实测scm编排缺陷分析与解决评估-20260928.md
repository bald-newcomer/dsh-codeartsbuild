## 2. 根因分析

### 2.1 根因 1（D1/D2）：repo_prepare"已有远端"分支输出语义不清

`repo_prepare` 对已有远端返回：

```json
{ "repository_uuid": null, "repo_id": null, "repo_name": "dsh-quant",
  "url": "https://codehub.devcloud.cn-north-4.huaweicloud.com/624d3c360116457693776843c45328a9",
  "web_url": "...", "ssh_url": "...", "existing_remote": true }
```

**问题**：
- 输出含 `url`（远端 HTTPS 地址）但 **`repo_id` 为 null**——而 `create_job.scms` 的 `repo_id` 是必填（FE-08 §1.5：`repo_id = RepoInfo.repoId` 数字主键）。
- 模型**无法从该输出推导 repo_id**：远端 URL 是 `https://codehub.../{projectUuid}/{repoName}`，**不含数字主键**——repo_id 只能经 `GetRepository` API 回读或用户提供。
- 模型反复尝试用 `url` 当 scm、或空 repo_id，全部 422。

**本质**：repo_prepare 的"已有远端"分支**只返回了 URL，没返回 repo_id**——对 create_job 而言信息不完整。模型无渠道补齐 → 反复硬试。

### 2.2 根因 2（D3）：失败后无转向机制

SKILL 强制规约 #6 写"重试上限 3 轮"，但：
- **模型不把 422/参数错误当作"需要求助"的信号**（错误是 E_PARAM，模型以为改参数就能过）。
- SKILL 未给出"连续同因失败 → 停止并求助"的可执行触发条件。

### 2.3 根因 3（D4）：agencyUrn 绕过通道

`create_job` 支持 `agencyUrn`（委托账号），模型最终用它 + 空 scms 成功——**合法但不合意图**（用户要"基于本地仓库创建任务"，空 scms 意味着云端任务无代码源，后续 run_job 无法构建）。契约对"scms 为空但传 agencyUrn"未设拦截。

### 2.4 根因 4（D5）：module_id 白名单执行弱

SKILL 规约写"module_id 全限定名且在实测白名单"，但模型在**本地设计文件**阶段就臆造了格式——说明白名单约束未在"组装前"生效（仅 create_job 校验，未在意图/设计阶段约束）。

## 3. 解决方案评估

### 方案 A：增强 repo_prepare 输出（补 repo_id 回读）

**做法**：repo_prepare 的"已有远端"分支，除返回 URL 外，**调 GetRepository 回读 repo_id**（远端 URL 含 projectUuid + repoName，可拼 `GET /v1/repositories/{uuid}`——但 URL 里是 projectUuid 不是 repository_uuid，需经 `ListRepositoryByProject` 按名查）。输出补 `repo_id`/`repository_uuid`。

| 维度 | 评估 |
|------|------|
| 修复面 | D1/D2 直接解决（模型拿到 repo_id 即可正确组装 scm） |
| 成本 | 中：repo_prepare 已有远端分支加 1-2 次 API 调用（ListRepositoryByProject 按名过滤 → GetRepository）；FE-08 §1.4 已实调这两个接口 |
| 风险 | 重名仓库需消歧（按 groupName/projectUuid 过滤）；失败回退现有行为 |
| 副作用 | repo_prepare 语义从"建仓/信息"扩展为"建仓/解析"——契约需更新 |

**判定**：**推荐**。直接消除根因 1，且接口已实测可用。

### 方案 B：SKILL 强化 scm 来源路由（编排指引）

**做法**：SKILL 仓库来源路由补明确规则：
- repo_prepare 返回 `existing_remote:true` 时 = **已有远端**，scm 来源应走"① 本地仓库已有远端解析 ② get_job/list_jobs 回读 ③ 用户提供 repo_id"，**禁止**用 URL 当 repo_id。
- create_job 报"repo_id 必填/仓库不存在"时：**停止重试**，按 §2.5 回溯 scm 来源渠道，仍不明 → 转人工。

| 维度 | 评估 |
|------|------|
| 修复面 | D2/D3 缓解（模型被指引不走歧路、及时求助） |
| 成本 | 低（纯文档） |
| 风险 | 依赖模型遵循指引——S1 已证明模型对规约遵循不稳定（D3 违规仍在） |
| 副作用 | 无 |

**判定**：**必做**（与方案 A 互补），但单独不足以根治（模型可能仍不遵循）。

### 方案 C：create_job 契约拦截"空 scms + agencyUrn"

**做法**：`validateScms` 增加：`scms 为空但 agencyUrn 存在` 时——不拦截（合法场景），但**返回结果附加提示**"任务无代码源（scms 为空），run_job 可能无仓库可构建；如需代码源请补 scms"。或对 scms 空 + 非 agencyUrn 场景维持现状。

| 维度 | 评估 |
|------|------|
| 修复面 | D4 缓解（模型被告知空 scms 的后果，避免"合法绕过"） |
| 成本 | 低（create_job.ts 校验加提示分支） |
| 风险 | 提示可能被模型忽略 |
| 副作用 | 需同步 api-contract 边界表 |

**判定**：**可选**（低成本防绕）。

### 方案 D：module_id 白名单前置校验

**做法**：SKILL 明确"**组装前** module_id 必须取实测白名单（step-templates.json / recommended_steps / list_templates 返回），设计/规划阶段不得自造 module_id 格式"；并在 repo_build 的 recommended_steps / list_templates 输出中强化白名单标注。

| 维度 | 评估 |
|------|------|
| 修复面 | D5 缓解 |
| 成本 | 低（SKILL + 契约标注） |
| 风险 | 模型遵循度问题同 B |
| 副作用 | 无 |

**判定**：**推荐**（与 B 一起作为 SKILL 强化包）。

### 方案 E：TEST-04 增加"scm 来源"专项断言

**做法**：TEST-04 S1 检查点强化：① repo_prepare 输出必须含 repo_id（或明确 existing_remote 且后续有补 repo_id 的动作）；② create_job 失败 ≤3 轮后必须求助；③ 禁止空 scms 绕过（除非用户确认）。

| 维度 | 评估 |
|------|------|
| 修复面 | 验证侧（确保修复落地后可被测试捕捉） |
| 成本 | 低（TEST-04 §3.1 检查点更新） |
| 风险 | 无 |
| 副作用 | 无 |

**判定**：**必做**（闭环验证）。

### 5.2 实现中的实测发现（偏离原方案）

1. ~~`/v1/projects/{uuid}/repositories` 对 dsh-quant 所在项目返回空~~ → **2026-09-29 用户决策：保持 per-project 接口**（`/v1/projects/{project_uuid}/repositories`，uuid=**入参目标项目**）；"返回空"的语义是**当前目标项目无此仓库**，正确动作是**允许在当前项目新建**，而不是去其他项目（全局 `/v2` 翻页）找。已回退全局翻页，改为 per-project 查询 + 未命中建仓。
2. **远端 URL 含真实 projectUuid**（`https://codehub.../{projectUuid}/{repoName}.git`）——不再用 URL 解析项目优先；查询项目固定为**入参目标项目**（仓库应建在用户指定的项目）。
3. **create_job 直传 repo_id 失败（403），需 repo_id + url 组合**——scms 组装细节待契约标注（后续迭代）。
