## 2. 根因分析

### 2.1 技能未被主动先加载：注册描述与 SKILL.md frontmatter 漂移

**机制链路**：模型在会话开始看到的是宿主注入的 `<available_skills>` 目录条目（`- codeartsbuild: <description>`）——条目描述来自插件 `src/entry/skill.ts` 注册时**硬编码的短描述**：

> "Huawei Cloud CodeArts Build 构建生命周期管理（dsh 插件形态）。本地仓库编译构建探索（subagent）、云端构建任务创建/编排、触发与停止、状态监控、产物与日志、失败诊断。"

而 SKILL.md frontmatter 的 `description`（富描述：触发词列表 + "使用本 skill 处理任何与 CodeArtsBuild 相关的构建工作"）**未被注册使用**——`skill.ts` 只解析 `name`，描述写死。即：**目录条目（模型唯一可见的触发依据）与 SKILL.md 单一事实来源漂移**，弱描述（能力罗列，无数值化触发指令）不足以让 35B 模型在 step1 就识别"此任务必须加载本技能"。

**次要因素**：SKILL.md 内"不要调 `list_agents` 查能力"等防错规约在技能加载前不可见（鸡生蛋）——模型 step1 连调 `list_agents`×2 正是规约缺位时的自然行为。

### 2.2 空 scms 先建：软提示机制失效（信息层 → 机制层）

FE-13 §2.3 已把 `scms_empty_hint` 升级为"操作路径引导"（含 repo_prepare→repo_push→create_job 顺序），但 ed0ef1ff 会话模型**仍忽略提示**（连续两会话证明软提示不可靠）。按 FE-17 机制化方法论（规约被反复违反 → 查工具强制能力 → 机制化 → 删行为约束、留参数引导），升级为 delete_job 同款 **need_confirmation 软拦截**。

### 2.3 && 便携性：复制命令未按宿主 shell 适配

repo_push next_actions / get_push_credential commands / repo_prepare push_guidance 中的命令串使用 `&&`（bash 语义）——Windows 宿主为 PowerShell 5.1（**不支持 &&**，会话实测撞墙）。宿主环境以 Windows 为主（SKILL compatibility 声明 bash（非 Windows）/ pwsh（Windows）），复制命令必须双 shell 兼容（`;` 为公共分隔符）。

## 3. 设计方案（逐条，均已落地）

### 3.1 P0：skill 注册描述与 SKILL.md frontmatter 单一事实来源对齐（机制层）

**改动**：
- `src/entry/skill.ts`：`parseFrontmatter` 扩展解析 `description` 折叠标量（`description: >` 后缩进行按空格拼接，容错 CRLF），注册描述取 `parsed.description`（缺省回落 `FALLBACK_DESCRIPTION`）；`whenToUse` 维持硬编码（frontmatter 无此键）。
- `skills/codeartsbuild/SKILL.md` frontmatter `description` 重写：**"【先加载再行动】...必须先调用 `skill` 工具加载本技能（name=codeartsbuild），再执行任何工具操作或仓库探索（含 glob/read/git/subagent 等）——不要先调 `list_agents` 探测子 agent 能力"** + 触发词列表（构建任务/编译构建/build job/跑构建/构建失败/构建产物/创建构建/云端构建/代码能编译吗等）。

**效果**：目录条目 = 富描述 + 数值化"先加载"指令 + 反模式提示 → 模型在 step1 即具备强触发依据；SKILL.md 改 description 一处，注册描述自动同步（消灭漂移）。

**测试**：entry-skill.test 增加断言 `description` 含 `先加载`（锁 frontmatter 驱动注册）。

### 3.2 P1：create_job 空 scms → need_confirmation 软拦截（机制层）

**现状**：`create-job.ts` 对空 scms 仅成功返回附 `scms_empty_hint`（信息层），任务已创建（副作用先于提示）。

**设计**（镜像 delete_job confirm 模式）：
- 新增入参 `confirmEmptyScms?: boolean`（默认 false，schema：`src/tools/parameters.ts`）。
- `scms` 为空且未确认 → **HTTP 调用之前**返回 `makeSuccessResult({ created:false, reason:'need_confirmation', scms_empty:true, next_actions:[...] })`——不创建、不产生缺陷任务；next_actions 引导：① 正确顺序 repo_prepare → repo_push → 带 scms 重试；② 已建任务用 update_job 补 scms；③ 确需无代码源（稍后补 scms / 运行期 scm 覆盖 / 委托账号）→ 用户确认后携带 `confirmEmptyScms=true` 重试。
- `confirmEmptyScms=true` → 维持原行为（创建 + `scms_empty_hint` 提示，含 agencyUrn 分支文案）。

**契约同步**：`docs/api/api-contract.md` §2.4 行 + `docs/api/tools/create_job.md`（参数表新增 `confirmEmptyScms` 行 + "空 scms 软拦截"注记替换原"不拦截"注记）+ SKILL.md 工具清单 create_job 行 + 强制约束 #6。

**测试**：create-job.test——无 scms 无确认 → `need_confirmation`（created:false，不发创建请求）；无 scms + confirmEmptyScms=true → 创建成功 + hint；`makeInput` 默认带 `confirmEmptyScms:true`（非 scms 场景测试走已确认路径）。

### 3.3 P1：SKILL 意图 1 补"本地非 git 仓库 git init 前置"（信息层）

**改动**：SKILL.md 意图 1「仓库来源路由」段后新增「本地非 git 仓库前置」：`repo_prepare` 只建远程仓、不 init 本地 git；`repo_push` 有 `not_git_repo` 预检——本地缺 `.git` 时先经宿主命令 `git init; git config user.email "<邮箱>"; git config user.name "<用户名>"; git add .; git commit -m "initial commit"`，再 repo_push。

### 3.4 P2：复制命令 `&&` → `;` 便携化（机制层，5 处）

- `src/providers/codeartsbuild/repo-push.ts`：`not_git_repo` next_actions（补 user.email/user.name + PowerShell 5.1 提示）、PROXY_AUTH、REJECTED_FETCH_FIRST、UNKNOWN、project_mismatch 共 5 处命令串 `&&` → `;`（并附"PowerShell 5.1 不支持 &&，命令用 ; 分隔或逐条执行"提示）。
- `src/providers/codeartsbuild/get-push-credential.ts`：`set_url_and_push` 命令串 `&&` → `;`。
- `src/providers/codeartsbuild/repo-prepare.ts`：`push_guidance` 命令串 `&&` → `;`。

**理由**：`;` 为 bash 与 PowerShell 公共顺序分隔符；命令串为模型复制到宿主 shell 执行的指引，双 shell 兼容是硬约束。
