## 2. 设计方案（逐条）

### 2.1 P1：repo_push 缺 remoteUrl 自动探测（机制层兜底）

**现状**：`repo-push.ts` 无 remoteUrl 时直接返回 `{pushed:false, reason:'missing_remote_url'}`（repo-push.ts:163-168）。

**设计**：缺 remoteUrl 时**自动从本地 git 远端探测**——`git remote -v` 解析 codehub 远端地址作为 remoteUrl 候选，再走既有 origin 预检/推送流程。探测顺序：

1. `input.remoteUrl` 显式传入（最高优先，现状保留）
2. `git remote get-url origin`（本地已有 origin 且含 codehub/devcloud）→ 解析为 remoteUrl
3. 本地多个远端中第一个含 codehub 的地址（对齐 repo_prepare 的 detectRemote 逻辑）
4. 探测失败 → 维持 `missing_remote_url` 结构化返回（不抛异常）

**边界**：
- 探测出的 origin 项目 UUID ≠ projectUuid → 走既有 `project_mismatch` 拦截（不推送）
- 探测出的是第三方 Git 平台 URL（github 等）→ 拒绝并提示先用 repo_prepare 建仓
- 本地非 git 仓库 → 维持 missing_remote_url

**改动**：`src/providers/codeartsbuild/repo-push.ts` 新增 `detectRemoteUrl(repoPath)` 辅助（复用 repo_prepare 的 parseProjectUuidFromRemoteUrl）。

**测试**：repo-push.test 新增——缺 remoteUrl + 本地 origin 为 codehub → 自动探测并推送；缺 remoteUrl + 本地 origin 为 github → 拒绝；缺 remoteUrl + 非 git 仓库 → missing_remote_url。

### 2.2 P2：宿主 git 操作规约（SKILL 强制约束）

**现状**：SKILL 无 git 操作规约，模型可自由用 pwsh 执行任意 git 命令（含 `git reset --hard`）。

**设计**：SKILL 强制规约新增 #11「宿主 git 操作安全」：

1. **禁止 `git reset --hard` / `git checkout -- .` / `git clean -f`**——破坏性命令会丢弃工作区/未提交变更（8155dd01 曾 `reset --hard` 致 src/ 丢失，靠 reflog 自救）；需要撤销变更时用 `git stash` / `git checkout -- <具体文件>`（指向性恢复）
2. **push 前确认工作区干净**：`git status` 确认无未提交变更；本地领先 origin 时直接 push，分歧时 `git pull --rebase`（不用 merge 避免多余合并提交）
3. **重试上限 3 轮**：git 命令失败读 stderr 分类（对齐 git-push.md 决策树），3 轮无果升级用户
4. **git 命令失败不 panic**：`exit code 1` 可能只是 msys DLL 噪音（8155dd01 多次 `CreateFileMapping`/DLL error 但命令实际成功）——先验证实际效果（`git log`/`git status`/`git push` 返回），再判断是否真失败

**落点**：`skills/codeartsbuild/SKILL.md` 强制规约 #11 + `references/git-push.md` 新增"宿主 git 安全操作"小节。

### 2.3 P3：SKILL 操作路径显式串联 repo_push

**现状**：意图 1 的代码块 `repo_build → create_job`，仓库来源路由文本提到 repo_prepare→repo_push 但无字段串联指引。

**设计**：

1. 意图 1 代码块改为：
   ```
   list_jobs(search=任务名) 查重 → repo_prepare(取 remote_url) → repo_push(remoteUrl=上一步 remote_url)
       → repo_build → create_job → run_job → wait_build → list_artifacts
   ```
2. 仓库来源路由补充字段串联：**repo_prepare 输出的 `remote_url`/`repo_id`/`url` 是 repo_push 与 create_job 的唯一输入来源**——repo_push 的 `remoteUrl` 参数直接取 repo_prepare 输出的 `remote_url`；create_job 的 `scms.repo_id/url` 取 repo_prepare 输出的 `repo_id/url`。禁止模型手拼或从别处猜测。

**落点**：`skills/codeartsbuild/SKILL.md` 意图 1 + `references/repo-source-routing.md` §2.1/§2.2 字段串联表。

### 2.4 P4：构建产物链路（upload-release 步骤引导）

**现状**：会话 buildNo=3 SUCCESS 但 list_artifacts=[]——TS 项目默认 language 组合 `npm-build` 无 upload-release，产物不交付。

**设计**（SKILL 层引导，非机制强制——是否上传产物是业务决策）：

1. 意图 1 补充产物交付说明：`list_artifacts` 为空时，检查任务 steps 是否含 `upload-release`（上传软件包到发布库）或 `upload-obs`/`build-image-swr`；用户需交付产物时补对应步骤
2. `language` 组合表补充说明：`JavaScript/npm` 默认组合含 `npm-build` + `upload-release`（查 step-templates.json 确认——实际组合为 `['npm-build', 'upload-release']`），会话中模型未用 language 而是手拼 steps 漏了 upload-release

**落点**：`skills/codeartsbuild/SKILL.md` 意图 1 + `references/language-combinations.md` 产物步骤说明。

### 2.5 P5：镜像版本号选用优化（照抄字面量 + 校验提示可行动）

**现状**：FE-11 §6.1 校验已机制拦截臆造镜像，但错误信息只报"不在可用列表"+ 列清单——模型被拦后仍需自行判断该用哪个，仍可能再补全错一次。且模型倾向把 `image_select` 值（`nodejs20`）当版本前缀补全成 `nodejs20.18.0`。

**根因**：模型不理解 **`image_select` 的值就是服务端认的字面量（不补全、不加补丁号、照抄即可）**——`nodejs20` 不是"Node 20 的缩写"，而是镜像的完整标识符。

**设计（三层）**：

1. **校验错误信息可行动化**（template-assembler.ts `validateStepImage`）：错误 details 追加**推荐值提示**——
   - 项目要求 Node≥20 场景：在报错信息里点名 `nodejs20`（"若项目需 Node≥20，可用 `nodejs20`（字面量，勿补全为 nodejs20.x）"）
   - 通用：报错时按语义相近排序候选（如臆造 `nodejs20.18.0` → 提示"可用最接近的 `nodejs20`"）
2. **SKILL/文档显式声明"字面量照抄"**：
   - `references/step-templates.md` 说明：`image_select` 值是**服务端镜像标识符字面量**——**照抄、不补全、不加补丁号**（`nodejs20` 就是它，不要写成 `nodejs20.18.0`）
   - `SKILL.md` 强制规约 #12「镜像字面量」：覆写 image 时**必须原样抄写** image_select 中的值，禁止补全/变体/加版本号后缀
3. **相近值匹配降级**（可选项）：模型若传 `nodejs20.18.0`，校验器识别"不在列表但前缀命中 `nodejs20`" → 错误提示直接给推荐值 `nodejs20`（非 E_PARAM 硬拦，而是提示修正；硬拦仍保留防止透传臆造值）

**落点**：

| 层 | 文件 | 改动 |
|----|------|------|
| 1 | `src/providers/codeartsbuild/template-assembler.ts` | `validateStepImage` 错误 details 追加推荐值（前缀匹配：臆造 `nodejs20.18.0` → 推荐 `nodejs20`） |
| 2 | `skills/codeartsbuild/SKILL.md` | 强制规约 #12「镜像字面量照抄」 |
| 2 | `skills/codeartsbuild/references/step-templates.md` | 说明 image_select 为字面量，照抄不补全 |
| 3 | `tests/template-assembler.test.ts` | +2 用例（臆造 `nodejs20.18.0` → 报错推荐 `nodejs20`；合法字面量放行） |

## 4. 风险与边界

- **P1 自动探测**：本地 origin 指向旧项目时，探测出的 remoteUrl 会被 project_mismatch 拦截（正确行为）；但若模型本意就是推送本地 origin（未先 repo_prepare），自动探测会"跳过建仓"直接推——**需在探测分支明确：无 remoteUrl 且探测到 origin 时，提示"是否已 repo_prepare 建仓"，避免跳过建仓流程**。
- **P2 规约**：仅 SKILL 层约束，模型可能不遵守；机制层无法拦截宿主 pwsh 命令（超出插件能力），靠规约 + 会话实测校验。
- **P4 产物**：上传产物是业务决策，SKILL 只引导不强制；误引导上传敏感文件需用户在 create_job 步骤确认。
- **P5 前缀推荐**：前缀匹配推荐（`nodejs20.18.0`→`nodejs20`）是**提示性**的，硬拦仍保留（防止臆造值透传）。前缀匹配需精确（`nodejs20.18.0` 前缀 `nodejs20` 命中；但 `nodejs2` 不应匹配 `nodejs20`——用"值或值+`.`"边界，避免过宽误推荐）。
