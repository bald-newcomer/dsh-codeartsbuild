## 0. 文档定位

b98a0fdc 会话（2026-10-26）暴露 `repo_build` 单次尝试局限：探测把 uv 项目当成 pip 项目生成 `pip install -r requirements.txt`（requirements.txt 不存在）→ 失败即返回 FAILED → 模型无 build info 可用，只能凭猜测编排云端构建。本文档设计**子 agent 自主探索方案**——让 AI 自己迭代跑通本地编译，输出固定 schema 的 build info JSON，主 agent 据此判断云端构建模板。

## 1. 问题清单（b98a0fdc 会话证据）

| # | 级别 | 问题 | 会话证据 | 影响 |
|---|------|------|---------|------|
| P0 | 高 | **`repo_build` 单次尝试局限**：探测→生成 1 条命令→跑 1 次→失败即 FAILED | turn 2.2 `repo_build` 输出 `status:FAILED`，`build_command:pip install -r requirements.txt`（requirements.txt 不存在） | 模型无 build info 可用，只能猜测编排云端构建 |
| P1 | 高 | **`probeRepo` 不识别现代 Python 项目管理器**（uv/poetry/pdm） | `pyproject.toml` 用 uv 管理依赖，`probeRepo` 只认 `requirements.txt`/`setup.py`/`pyproject.toml`，统一返回 `python` + `pip install -r requirements.txt` | uv/poetry/pdm 项目探测即生成错误命令 |
| P2 | 中 | **构建环境信息缺失**：跑通后未输出 python_version / uv_version 等环境版本 | `repo_build` 输出无 `build_environment` 字段 | 云端构建无法对照本地环境选镜像 |
| P2 | 中 | **云端构建指导缺失**：跑通后未输出 `cloud_build_guidance`（image/deps_command/build_command/steps） | 模型需自行参照 list_templates/get_job 其他任务配置猜模板 | 模型跨项目参照配置（违反项目隔离），且模板选择易错 |

### 多策略迭代方案的局限评估

会话讨论了"多策略迭代"方案（`buildStrategies(probe)` 生成 N 条候选命令逐个尝试），但用户明确指出局限：**本质仍是预设命令列表，无法应对手写 Makefile、自定义构建脚本、未知项目管理器等场景**。真正需要的是让 AI 自主探索跑通编译。

## 2. dsh 运行时子 agent 能力调研

### 2.1 dsh 运行时确有完整子 agent 能力

调研 `node_modules/@deepseek-ai/dsh-subagent` 确认：

| 包 | 职责 |
|----|------|
| `@deepseek-ai/dsh-subagent` | 子 agent 服务入口：提供方注册表、启动与继续 API、生命周期事件 |
| `@deepseek-ai/dsh-subagent-spawn-in-process` | 进程内 spawn 提供方（最易组合） |
| `@deepseek-ai/dsh-tool-subagent` | 面向模型的委派工具（让主 agent 调用 spawn 子 agent） |
| `@deepseek-ai/dsh-subagent-fork-in-process` | 进程内 fork 提供方 |

### 2.2 子 agent 两种形态

| 形态 | 语义 | 适用场景 |
|------|------|---------|
| **一次性（one-shot）** | 运行一次，以单个结果结算，可附带结构化输出 | **本地构建探索**（跑通即返回 build info） |
| 可继续（continuable） | 保留持久会话，按顺序接受后续消息 | 不适用（构建探索是一次性任务） |

### 2.3 子 agent 关键能力

- **工具限制**：`ToolRestriction` 类型支持 `allowedTools`/`disallowedTools`——可限制子 agent 只用宿主命令工具（pwsh/bash/read/glob/grep），**不触及云侧工具**
- **深度预算**：`delegationDepth` 防止无限递归
- **隔离性**：子 agent 崩溃/异常无法破坏父级会话
- **结果传递**：一次性子 agent 的最终输出作为工具结果返回给主 agent

### 2.4 启用方式（宿主配置，非插件自配）

子 agent 能力是**宿主能力**，需在 cordis 配置中挂载：

```yaml
# cordis.patch.yml / profile 装配
plugins:
  - name: '@deepseek-ai/dsh-subagent'
  - name: '@deepseek-ai/dsh-subagent-spawn-in-process'
  - name: '@deepseek-ai/dsh-tool-subagent'
    config:
      provider: spawn
      toolName: subagent
```

挂载后主 agent 看到 `subagent` 工具，可调用它 spawn 子 agent。**插件自身不改**（apply 入口仍只注册 18 个 codeartsbuild_* 工具——本方案不新增工具；后续 FE-15 追加 `get_push_credential` 后为 19 个）。

## 3. 设计方案

### 3.1 核心思路：主 agent 编排 + 子 agent 探索

```
主 agent 意图 1 流程 → 遇到"本地构建验证"环节
  → 调用宿主 subagent 工具 spawn 子 agent（prompt 内嵌 build info schema + 探索流程）
  → 子 agent 自主探索：pwsh 跑命令 → 看错误 → 改命令 → 再跑 → 跑通
  → 子 agent 返回固定 schema 的 build info JSON
主 agent 拿 JSON → 用 build_environment / build_command / build_artifacts 判断云端模板
  → create_job（主 agent 自决模板选择）
```

**职责分离**：
- **子 agent**：只负责本地跑通编译，输出 build info JSON（环境/命令/产物）——**不关联云端**
- **主 agent**：拿 build info 判断云端模板（image/steps 等）——**模板选择在主 agent**

### 3.2 子 agent prompt 设计

子 agent 的 prompt 由 SKILL 在编排路径中构造（主 agent 调 `subagent` 工具时传入）。prompt 内嵌：

1. **任务目标**：跑通本地仓库编译，输出 build info JSON
2. **输出 schema**（固定，子 agent 必须按此结构返回）
3. **探索流程指引**（探测环境→试命令→迭代→固化）
4. **约束**：重试上限 5 轮；只读不修改源码；不调云侧工具

### 3.3 子 agent 输出 schema（build info JSON）

```json
{
  "status": "SUCCESS | PARTIAL | FAILED",
  "repo_path": "D:/code/.../yfinance-mcp",
  "repo_type": "python",
  "build_tool": "uv",
  "lockfile": "uv.lock",
  "build_environment": {
    "python_version": "3.10.2",
    "uv_version": "0.4.20",
    "node_version": null,
    "os": "win32"
  },
  "build_command": "uv sync && uv build",
  "build_artifacts": [
    {"name": "yfmcp-0.6.0-py3-none-any.whl", "path": "dist/", "size_bytes": 12345}
  ],
  "attempted_commands": [
    {"command": "pip install -r requirements.txt && python -m build", "exit_code": 1, "error": "No such file: requirements.txt"}
  ]
}
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `status` | string | ✅ | `SUCCESS`=跑通；`PARTIAL`=跑通但有警告；`FAILED`=5 轮未跑通 |
| `repo_path` | string | ✅ | 仓库绝对路径 |
| `repo_type` | string | ✅ | 仓库类型（python/npm/maven/go/...） |
| `build_tool` | string | ✅ | 实际跑通的工具（uv/pip/npm/mvn/...） |
| `lockfile` | string \| null | ✅ | 锁文件名（uv.lock/package-lock.json/pom.xml/...） |
| `build_environment` | object | ✅ | 跑通时的环境版本（仅含实际相关的字段，null 表示未探测） |
| `build_command` | string | ✅ | 实际跑通的命令（FAILED 时为最后尝试的命令） |
| `build_artifacts` | array | ✅ | 产物清单（FAILED 时为空数组） |
| `attempted_commands` | array | ✅ | 所有尝试过的命令 + 各自错误（SUCCESS 时至少含跑通的那条） |

**注意**：子 agent **不输出** `cloud_build_guidance`（image/steps 等）——云端模板选择由主 agent 判断。

### 3.4 主 agent 编排（SKILL 意图 1 改造）

```
意图 1：从零到完成（本地构建 → 云端任务 → 产物）

repo_prepare(取 remote_url/repo_id)
  → repo_push(remoteUrl=上一步 remote_url, accessToken=用户提供)
  → subagent(prompt=本地构建探索, 返回 build info JSON)        ← 新增
  → 主 agent 解析 build info → 判断云端模板（image/steps）
  → create_job(主 agent 自决 steps/stepsPlan)
  → run_job → wait_build → list_artifacts
```

**关键变化**：原 `repo_build` 单工具调用 → 替换为 `subagent` 工具调用（由宿主提供）。`repo_build` 工具保留作为**可选固化**（子 agent 跑通后可调一次 repo_build 留档，双保险）。

### 3.5 子 agent 工具限制

子 agent 的 `allowedTools` 限定为：
- `pwsh` / `bash`（宿主命令工具，跑构建命令）
- `read` / `glob` / `grep`（读文件、探测仓库结构）

**不包含**：任何 `codeartsbuild_*` 工具（云侧工具）——子 agent 不触及云端。

## 5. 风险与边界

- **宿主未挂载 subagent 能力**：SKILL `compatibility` 段声明依赖；未挂载时主 agent 回退到原 `repo_build` 单次尝试（向后兼容）。
- **子 agent 无限试错**：prompt 强约束"重试上限 5 轮，无果返回 FAILED + attempted_commands"；`delegationDepth` 兜底。
- **子 agent 输出 schema 不固定**：prompt 内嵌 schema 模板 + 示例；主 agent 解析时容错（缺字段视为 null）。
- **子 agent 修改源码**：prompt 约束"只读不修改"；`allowedTools` 不含 Edit/Write（宿主命令工具的文件写入能力由沙箱拦截）。
- **repo_build 工具去留**：保留作为可选固化（子 agent 跑通后调一次 repo_build 留档）；也可废弃（子 agent 输出已含 build info）。**本设计倾向保留**——子 agent 不保证调 repo_build，主 agent 可选调。
