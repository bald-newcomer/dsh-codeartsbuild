## 0. 文档定位

本文档是**「本地/远端仓库 → create_job 构建任务创建」链路的工作流优化设计**，回答"创建任务的 AI 编排如何避免失败"——从一次失败的人工测试轨迹提炼 6 个问题点，逐条给出优化方案（模板选择、scm 字段来源、本地/远端仓库支持、list_templates 扩展）。

**设计原则（沿用工程规约）**：
- **契约驱动**：scm 字段契约以 api-contract.md §2.4 与 FE-03 §3.2 实测字段为准；未实测字段标注"**待确认**"，禁止臆造。
- **来源强制**：与 AGENTS.md「核心主键」表同构，建立 scm 字段"来源渠道"强制表（§2.5 O5），字段必须取自正确前置渠道。
- **文档先行**：本方案仅落定设计，编码为待办（§5），不在此臆造契约。

## 1. 问题分析（人工测试轨迹提炼）

> 轨迹：用户指定**本地仓库** `D:\code\ai\dsh-quant`（TypeScript/npm 项目），意图「创建 codeartsbuild 构建任务」。完整会话失败，卡在 `create_job` 的 scm 字段推测。以下 6 个问题点逐条给出轨迹证据（引用实际工具调用/错误）。

### P1 模板选择逻辑：模型错误地从 npm 模板切到 Shell 模板

**轨迹证据**：
- `list_templates {"pageSize":100}` 返回了官方 npm 模板（uuid `00014`），但模型判断：
  > "npm 模板是 `npm run build` 但 dsh-quant 是 TypeScript 项目用 `tsc` 编译，改用 Shell 模板"
  > "npm 模板的构建命令是 `npm run build` 但我们的项目需要更完整的构建流程（`npm ci && npm run build && npm test`）"
- 随后模型决定使用 `Shell` 模板（自定义 command）。

**根因**：模型以**项目具体构建命令**而非**构建环境/语言族**为锚点选择模板。npm 模板本质是 **node 构建环境**（image `nodejs12.7.0` + `command` 可覆盖），TS 项目的编译环境与 npm 等价，**应直接用 npm 模板并在 properties.command 覆盖为 `npm ci && npm run build && npm test`**，而非降级到通用 Shell。

**影响**：Shell 模板 `20017` 需手工拼完整命令与 image，丧失 npm 模板的默认环境/依赖管理，易出错且语义退化。→ 方案 **O1**。

### P2 本地仓库不受支持：create_job 需远端仓库，本地仓库直接卡死

**轨迹证据**：
- 用户意图的仓库是**本地路径** `D:\code\ai\dsh-quant`（会话工作区）。
- 模型反复尝试后意识到："由于 dsh-quant 在 GitHub 上，我们需要先在华为云 CodeHub 中链接或导入该仓库"、"需要先有一个 CodeHub 仓库……先在 CodeHub 中链接或导入"，最终流程中断转向"问用户代码仓库信息"后**会话失败/取消**。

**根因**：`create_job` 的 scm 绑定的代码源必须是**云端可拉取仓库**（CodeArtsRepo / codehub），纯本地仓库无远端地址，无法直接创建。当前工具链无"本地仓库自动推送远端"或"远端仓库先拉取本地构建"能力。→ 方案 **O3 / O4**。

### P3 SCM 字段由模型臆造，导致 create_job 连续失败

**轨迹证据**（连续 3 次失败）：
1. 模型先用 **GitHub 仓库 URL / 臆造 scm** 创建 → `Error: [E_API] CreateNewJob 成功但响应缺 result.job_id`
2. 改用 `scm_type=gitlab` → 同样 `[E_API] CreateNewJob 成功但响应缺 result.job_id`
3. 改用 `sourceCode=pipeline` → `Error: [E_PARAM] 参数错误（422）: 仓库不存在或仓库已被删除`

**根因**：模型在 scm_type/repo_id/repo_name/url 等字段上**自由构造**（gitlab、github URL、pipeline），既不是实测字段（当前实测量测为 `codehub` + `repo_id`），也不是来自某前置渠道的强制来源。**没有 scm 字段"来源强制"规约**，模型臆造必然失败。→ 方案 **O5**。

### P4 模型不识别已有任务的有效 scm 配置，直到失败后才回看

**轨迹证据**：
- 失败 3 次后，模型才调用 `list_jobs` 查看已有任务，发现"已有任务使用的 `scmType` 是 `codehub`，并且有 `repoId`"，才意识到正确参数格式。

**根因**：SKILL 建议操作路径未在 create_job 前链路**强制先 `get_job`/`list_jobs` 参考已有任务 scm 配置**，导致模型盲猜后失败才回看。应在建议路径中明确：**create_job 组装 scm 前，先 `get_job`（或 `list_jobs`）抽取已验证的 scm 字段结构**。→ 方案 **O5（前置渠道）+ 3 SKILL 建议**。

### P5 list_templates 仅查官方模板，未覆盖用户自定义模板

**轨迹证据**：
- 模型 `list_templates {"name":"TypeScript"}` → `{"templates":[],"total":0}`（官方模板无 TS/npm 专属，需 pageSize:100 翻全量）。
- 全程未查询**用户在本项目/域中已自建的模板**，若存在适配该项目语言的用户自定义模板本可直接推荐。

**根因**：FE-03 §2.12 明确 `list_templates` 仅暴露**官方模板**（`ListOfficialTemplate` / `/v1/template/officialtemplates`），用户自建模板 `ListCustomTemplate`（`/v1/template/custom`）"后续扩展"，本期未落地。→ 方案 **O2**。

### P6 远端仓库流程缺"先拉取本地验证"策略

**轨迹证据**：
- 模型识别到需要 codehub 仓库 + repoId 后，停留在"需要创建/导入仓库"，**没有先通过本地 `repo_build` 验证 dsh-quant 编译通过，再关联云端仓库创建任务**；也未走"远端仓库 clone 本地 → repo_build → create_job"。

**根因**：远端仓库链路缺失"本地构建验证前置"回流：当前建议路径（意图 1）是 `repo_build → create_job`，但当 scm 是**远端仓库**时，应先克隆到本地、`repo_build` 验证编译、再创建任务，保证"本地通过才上云"。→ 方案 **O4**。

## 2. 优化方案（逐条）

### 2.1 O1 模板选择"环境锚点"原则

**原则**：选择 step 模板时，锚点是**构建环境 / 语言族**，不是项目具体构建命令脚本。

| 锚点（语言族/构建环境） | 适配模板 | module_id | 构建命令如何处理 |
|--------------------------|----------|-----------|------------------|
| TypeScript / JavaScript / Node / 前端 | **npm 模板** | `20014`（Npm构建） | 用项目 scripts 覆盖 `properties.command`（如 `npm ci && npm run build && npm test`），image 默认 `nodejs12.7.0`（可换 node 版本） |
| Java / Maven | Maven 模板 | `20043` | 覆盖 command |
| Java / Gradle | Gradle 模板 | `20008` | 覆盖 command |
| Go | Go 模板 | `20026` | 覆盖 command |
| Python | PyInstaller 模板 | `20015` | 覆盖 command |
| C/C++/CMake | CMake 模板 | `20005` | 覆盖 command |
| 其它/通用（无专用模板） | Shell 模板 `20017` | `20017` | 自定义 command + image **兜底用**，非首选 |

**判断规则**（写入 SKILL 与 FE-04 §1）：
1. **语言类型 ≠ 构建命令**：同语言不同 scripts 不应改变模板选择，只改 `properties.command`。
2. **前端口径优先**：`repo_build` 返回的 `repo_type`（如 `npm`）与 `recommended_steps[].module_id` 是模板选择的**强信号**（已实测对齐）。
3. **npm 覆盖 TS/JS/Node**：TypeScript/JavaScript/Node 一律落 npm 模板（构建环境等价），不因"用了 tsc"而改用 Shell。
4. **Shell 为兜底**：仅当语言无维护模板（FE-04 §1 不维护插件列表）或无语言识别时，才用 `20017` shell 自定义。

> **影响**：修正 FE-04 §1 语言组合表 `JavaScript/npm` 行——补充「TS/JS/Node 均归 npm 环境锚点」，并在该节说明"构建命令以 properties.command 覆盖，不改变模板选择"。

### 2.2 O2 list_templates 查询用户自定义模板

**目标（2026-09-23 用户澄清后修正）**：`list_templates` 工具**仅查询用户自定义模板**（`ListCustomTemplate`，v1 `/v1/template/custom`），作为创建构建任务前检查"是否有可直接使用的用户自建模板"。**官方模板（`ListOfficialTemplate`）不在工具查询范围**——仅作 `step-templates.json` 步骤模板库的离线初始化数据源（见 FE-04 §6 来源与刷新）。

**接口实测（2026-09-23 metaRepo YAML + 真实 HTTP 实调完成）**：

| 项 | 实测结论 |
|----|----------|
| **URL** | `GET /v1/template/custom`（metaRepo YAML `Request.Path` + 真实 HTTP 实调 200） |
| **参数** | `filter`(string)? / `name`(string)? / `page`(integer, ≥1)? / `page_size`(integer, ≤100)? / `tags`(string)?（全部 query，均可选） |
| **响应** | `result.items[]` + `result.total_size`——与 `ListOfficialTemplate` **完全同构**（实调确认）；item 含 `uuid`/`id`/`name`/`scope`(`custom`)/`type`/`description`/`favourite`/`nick_name`/`template.steps[]`/`parameters`，另多 `create_time`/`update_time`/`user_id`/`user_name`/`domain_id`/`domain_name`/`tool_type`/`i18n` 等自定义模板特有字段 |

**设计（已实现，2026-09-23）**：

| 项 | 设计 |
|----|------|
| **工具名** | 保留 `list_templates`（仅改查询对象为自定义模板） |
| **入参** | name? / page? / pageSize? / filter? / tags?（与实测参数一一对应） |
| **handler** | 调 `ListCustomTemplate`（GET `/v1/template/custom`）→ 规范化（与官方模板同构：items[] → templates[]，template.steps 提取到顶层） |
| **输出** | `{ templates, total }`；templates[] 含 uuid/name/description/scope/favourite/nick_name/create_time/user_name/steps |
| **module_id 约束** | 自定义模板的 `template.steps[].module_id` 同样须满足全限定名 + 白名单（FE-03 §3.3），可作 `create_job` steps 来源，禁止臆造 |
| **create_job 组装** | 维持现状（bundle 内打包 step-templates.json），不依赖在线官方模板查询 |

> **规约**：与 §2.1 O1 联动——创建任务前先 `list_templates` 查用户自定义模板（按语言/环境匹配）；无匹配时用 bundle 内 step-templates.json 的 `language` 组合或 `stepsPlan`。空结果不应视为"无可用模板"，应回退本地语言组（npm 等）。

### 2.3 O3 本地仓库自动推送至 CodeArtsRepo（新功能，待办）

**场景**：用户指定**本地仓库**（无远端或不愿手工推送）创建任务。当前 create_job 需云端仓库，本地仓库需先推送。

> **前置知识**：**CodeHub 即 CodeArtsRepo**——CodeArts Build 的 `scm_type=codehub` 对应华为云代码托管服务 CodeArtsRepo（原 CodeHub），仓库/仓库组在 CodeArtsRepo 中管理。

**设计（标注为待办，需实测 CodeArtsRepo 建仓接口）**：

```
本地 git 仓库（repoPath）
  ├─ 检测：是否 git 仓？有无远程（git remote -v）？
  │    ├─ 已有远端（scm_type=codehub，repo_id 可解析）→ 走 O4 远端流程
  │    └─ 无远端 / 纯本地 →
  │        ① 经 CodeArtsRepo 创建空仓（含项目/命名空间）
  │        ② git remote add origin <repo_url> && git push
  │        ③ 取得 repo_id / repo_url / web_url
  │        ④ 回填 create_job.scms（见 §2.5 O5 映射表）
  │        ⑤ 本地 repo_build 验证编译通过后 create_job
```

**待办要点**：
- 新增工具或 `repo_build` 扩展：`ensure_remote` / `push_to_codearts`（决策点：独立工具 vs 内置于 repo_build，见 §5 待办 #24）。
- **依赖实测**：CodeArtsRepo 建仓/推送接口（`repo_id`、`web_url` 如何回填）、CodeArtsRepo 与 Build 项目空间的关联。**未实测前标注"待确认"**。
- **失败回流**：建仓/推送失败 → 交互升级用户（用户可手工推送后走 O4）。

### 2.4 O4 远端仓库流程：先拉取本地构建，通过后再创建任务

**场景**：scm 是**远端 CodeArtsRepo (codehub)** 仓库。规避"未验证编译就创建任务"与"仓库不存在"臆造。

**流程**：

```
远端 codehub 仓库（已知 repo_id / url / branch）
  ├─ ① git clone <repo_url> -b <branch> 到本地工作目录
  ├─ ② repo_build（本地构建验证）→ 编译通过（SUCCESS）？
  │    ├─ 否 → 修复自解 → 重试 repo_build；无果升级用户（FE-01 §5）
  │    └─ 是 →
  ├─ ③ create_job（scm 取克隆仓库的 repo_id / url / branch，见 §2.5 映射表）
  └─ ④ run_job → wait_build → list_artifacts
```

**scm 字段映射表（O4 与 O5 共用，实测字段为准）**：

| scm 字段 | 来源渠道 | 获取方式 | 实测状态 |
|----------|----------|----------|----------|
| `scm_type` | **固定为 `codehub`** | CodeArtsRepo/codehub 仓库；当前实测唯一支持 | ✅ 实测（已有任务 `scmType: "codehub"`） |
| `repo_id` | CodeArtsRepo 仓库 ID | 建仓返回 / 已有任务 `get_job` 回读 / `list_jobs` 已有任务 scm | ⚠️ codehub+repoId 实测，字段名待确认（`repo_id`） |
| `repo_name` | CodeArtsRepo 仓库名 | 建仓返回 / 已有任务回读 | ⚠️ 待确认 |
| `branch` | 用户指定 / 仓库默认分支 | 默认 `master`/`main`；`run_job` codeBranch 参数指定 | ⚠️ create_job scm.branch 服务端支持**待确认**（run_job 分支经 parameter 生效，见 FE-03 §2.6） |
| `url` | 仓库克隆 URL | 建仓返回 / 已有任务回读 | ⚠️ 待确认 |
| `web_url` | 仓库页面 URL | 建仓返回 / 已有任务回读 | ⚠️ 待确认 |
| `build_type` | 默认 | 留空用默认 | ⚠️ 待确认 |

> **回流规约**：`create_job` 组装 scm **前**，若本地仓库有远端则取本地远端信息；若为远端仓库流程，`repo_id`/`url`/`web_url` **必须**取自克隆/建仓的实际返回，禁止模型手填 Git 平台第三方 URL（如 GitHub/gitlab）——CodeArts Build 只认 CodeArtsRepo(codehub) 仓库。

### 2.5 O5 SCM 字段来源强制规约（禁止臆造）

与 AGENTS.md「核心主键」表同构，建立 **scm 字段 ← 来源渠道** 强制映射，字段值必须取自指定前置渠道，**不明确字段转人工确认，禁止臆造**：

| scm 字段 | 来源渠道（强制） | 是否可臆造 |
|----------|------------------|-----------|
| `scm_type` | 实测唯一的 `codehub`；其它枚举（gitee/github/gitlab 等）**未实测，禁用** | ❌ 禁止 |
| `repo_id` | ① CodeArtsRepo 建仓返回 ② `get_job`/`list_jobs` 已有任务回读 ③ 本地已有远端仓库解析 | ❌ 禁止 |
| `repo_name` | 建仓返回 / 已有任务回读 | ❌ 禁止 |
| `url` | CodeArtsRepo 仓库 URL（建仓/回读），**非**第三方 Git 平台 URL | ❌ 禁止 |
| `web_url` | 建仓返回 / 已有任务回读 | ❌ 禁止 |
| `branch` | 用户指定 / 默认分支 | ✅ 可默认（master/main），但服务端支持待确认 |
| `build_type` | 默认，留空 | ✅ |

**前置渠道（create_job 组装 scm 前必走其一）**：
1. **本地仓库有远端**（codehub）→ 从本地 `git remote` 解析 repo_id/url/branch。
2. **远端仓库流程（O4）** → 从克隆/建仓硬返回回填。
3. **参考已有任务** → 先 `get_job`（或 `list_jobs`）抽取已验证 scm 结构（轨迹 P4 正例）。
4. **上述均不可得** → **转人工确认**仓库来源，禁止臆造后重试。

**错误回流**：`create_job` 返回 `E_API`「仓库不存在或仓库已被删除」（422，轨迹 P3）时，强制回溯 scm 来源渠道（是否臆造了第三方 repo_id/url），不继续换 scm_type 重试。

## 3. SKILL 修改建议

对 `skills/codeartsbuild/SKILL.md`「建议操作路径 / create_job 规约」的具体修改点：

### 3.1 意图 1（从零到完成）create_job 前链路扩展

原文：`repo_build → create_job → run_job → wait_build → list_artifacts`

**修改**：明确 create_job 前**仓库来源路由**——

```
[确定仓库类型]
  本地仓库: 检测远端 → 无远端 → O3 推送 CodeArtsRepo（待办）
                         → 有远端(codehub) → repo_build 验证 → create_job(取本地远端 scm)
  远端仓库(codehub): git clone 本地 → repo_build 验证编译通过 → create_job
列表模板: list_templates（官方+自定义 O2）
参考 scm: 不明确时 get_job/list_jobs 取已有任务 scm 结构（禁止臆造）
```

### 3.2 强制规约补充：模板选择环境锚点（O1）

在 create_job 的 steps 三选一说明处补充：
> 选择 step 模板以**构建环境/语言族**为锚点（TS/JS/Node → 用 npm 模板 `20014` 并覆盖 `properties.command`），**不以具体构建脚本切换模板**；Shell 模板 `20017` 仅兜底。参考 FE-07 §2.1。
