> **文档编号**: CAB-FE-017
> **类型**: 独立迭代特性设计（模板选用标准机制化 + imageSource 评估移除 + module_id 选用优化 + update_job 字段契约 + delete→update 优先优化）
> **日期**: 2026-11-05
> **状态**: ✅ 已实施（290 测试全绿 + tsc 通过；2026-11-05 落地）
> **上游依赖**: FE-15（凭据机制化）、FE-16（推码分支预检与模板字段契约）、FE-11（step 模板可用版本枚举迁移）
> **触发事件**: `docs/example/dsh-session-session-652fb005-7048-4a3f-9922-e7c1fafa7349.zip`（2026-11-05 实测）——"按 llm-quant 仓库创建 codeartsbuild 构建任务"全流程，4 轮构建失败（pip/apt 不在 shell 镜像 / command 丢失 / imageSource 拦截开销）

---

## 0. 文档定位

652fb005 会话（2026-11-05）暴露 FE-13/14/15/16 修复后仍存在的 5 类问题：

1. **模板选用标准错误**：模型把 shell-command 当成通用模板用，但 shell-command 镜像 `shell4.2.46-git1.8.3-zip6.00` 不含 Python/Maven 等语言运行时——选模板应按**核心构建工具**（python→pyinstaller-build，maven→maven-build），shell-command 仅用于无语言运行时的纯 shell 任务
2. **imageSource 拦截开销大**：FE-16 §2.2 的 imageSource 软引导每次都拦（[454]），但本次会话证明它没有正向价值（imageSource 不影响构建成败，只增加一轮调用开销）
3. **module_id 选用错误**：[415] 模型用了 `com.hw.codearts.build.module.linux.shell.command`（裸包名非白名单），白名单拦截但模型不知道完整白名单值
4. **update_job 路径字段契约**：[973] update_job 后 command 字段丢失——虽 FE-16 §2.1 已通过 assembleConfig 校验，但 update_job 路径需确认校验链完整
5. **构建失败优先 delete 重建而非 update 修复**：4 次 delete_job(confirm=true) 重建，违反 SKILL 规约 #10 的"优先 update_job 修复"

本文档设计这 5 类修复，**核心思路是模板选用规约机制化 + 移除 imageSource + 强化"优先 update 而非 delete"**。

## 2. 设计方案（逐条）

### 2.1 P0：模板选用标准机制化（按核心构建工具选模板）

**现状**：模型凭"shell-command 看起来通用"误用——shell-command 镜像 `shell4.2.46-git1.8.3-zip6.00` 是精简 shell 镜像（含 git/zip 不含 Python/Maven 等）。每个 step-template 的默认镜像对应一个**核心构建工具**（pyinstaller-build→python3.x，maven-build→maven3.x，npm-build→nodejs）。

**用户决策**（2026-11-05）：所有 step-template 都包含基础工具（shell/git/zip 等），**选用标准是核心构建工具**，不是 shell。如本次构建核心是 Python → 应选 pyinstaller-build（镜像含 python3.x），覆盖 command 为 `pip install + pytest` 即可。

**设计**（三层）：

1. **step-templates.json 加 `core_tool` 字段**：每个模板标注核心构建工具（如 `python` / `maven` / `npm` / `go` / `shell-only` / `docker` 等），让模型一眼看出每个模板的运行时环境。

2. **`resolveStep` / `validateStepsPlanRefs` 加模板选用引导**：当模型传 `shell-command` 但项目语言已知（从 subagent build_info 或 cwd 探测）是 python/maven 等时，返回 `template_mismatch` 警告（不阻断）：
   - 警告信息：`shell-command 模板的镜像 shell4.2.46 不含 Python 运行时——若需跑 pip/pytest，应改用 pyinstaller-build（镜像 python3.x，覆盖 command 为 'pip install + pytest'）`
   - next_actions：列出对应核心工具的模板

3. **SKILL 规约强化**（§工具清单或新规约 #15）：
   - **选用标准**：按核心构建工具选模板（python→pyinstaller-build，maven→maven-build，npm→npm-build，go→go-build），shell-command 仅用于无语言运行时的纯 shell 任务（如脚本调度、文件操作）
   - **command 覆盖**：每个模板的默认 command 都可被 properties.command 覆盖（如 pyinstaller-build 默认 `python -m PyInstaller`，覆盖为 `pip install -r requirements.txt && pytest` 即变 Python 测试任务）
   - **image 不要擅自换**：每个模板的 image_select 已对齐核心工具，shell-command 不要换成 python3.x（image_select 不含）

**落点**：
- `src/providers/codeartsbuild/assets/step-templates.json`（加 `core_tool` 字段）
- `src/providers/codeartsbuild/template-assembler.ts`（`resolveStep` 加 mismatch 警告；`TEMPLATE_BY_ID` 暴露 core_tool）
- `skills/codeartsbuild/SKILL.md`（规约 #15 模板选用标准）
- `skills/codeartsbuild/references/step-templates.md`（模板表加 core_tool 列）

### 2.2 P1：imageSource 机制评估 → 移除

**现状**：FE-16 §2.2 的 `imageSource` 软引导每次 create_job 传 image 覆盖都拦一轮（[454] need_image_source → 模型带 imageSource 重试）。本次会话证明：
- **无正向价值**：imageSource 不影响构建成败（FE-11 的 `validateStepImage` 已硬拦臆造 image）；imageSource 只是来源标记，对实际构建无影响
- **增加开销**：每次 create_job 多一轮调用；模型被拦后只学到了"带 imageSource 重试"，没有提升 image 选择的正确性

**用户决策**（2026-11-05）：评估不需要 imageSource。

**设计**：**移除 imageSource 机制**——
- `src/providers/codeartsbuild/create-job.ts`：删除 `imageSource` 入参与 `need_image_source` 软引导逻辑
- `src/tools/parameters.ts`：删除 createJobParameters 的 imageSource 字段
- `tests/create-job.test.ts`：删除 imageSource 相关 5 个用例（[454] 类用例）
- `docs/api/api-contract.md` / `docs/api/tools/create_job.md`：删除 imageSource 描述
- `skills/codeartsbuild/SKILL.md`：规约 #12 删除 imageSource 软引导段，保留"镜像字面量照抄"硬约束（FE-11）

**保留**：FE-11 的 `validateStepImage`（硬拦臆造 image 值）+ FE-16 §2.1 的 `validateStepProperties`（硬拦字段名错误）——这两个机制有实际价值。

### 2.3 P1：module_id 选用错误优化

**现状**：[415] 模型用 `com.hw.codearts.build.module.linux.shell.command`（裸包名），白名单是 `devcloud2018.codeci_action_20017.action`（带版本号的 action 全限定名）。模型凭相似性猜包名，不知道完整白名单值。

**根因**：模型从 KooCLI 文档或 OpenAPI 看到的 module_id 是裸包名 `com.hw.codearts.build.module.linux.shell.command`，但 CodeArtsBuild 服务端实际要求的是 `devcloud2018.codeci_action_<N>.action` 全限定名（含版本号）。

**设计**：

1. **白名单拦截错误信息增强**：当前 `validateSteps` 拦截时只列"必须取自 recommended_steps / list_templates / 实测白名单"——补**完整白名单值列表**（前 5 个 + 总数），让模型直接复制：
   - 错误信息追加：`可用 module_id（白名单，共 14 个）: devcloud2018.codeci_action_20043.action (maven-build), devcloud2018.codeci_action_20017.action (shell-command), ...——stepsPlan 用 template_id（如 maven-build），steps 数组用全限定 module_id`

2. **`validateStepsPlanRefs` 同步增强**：stepsPlan 用 template_id（推荐），拦截时列完整 template_id 清单（已有，但补 module_id 对照）。

3. **SKILL 规约强化**：明确"stepsPlan 用 template_id（如 maven-build），steps 数组用 module_id（如 devcloud2018.codeci_action_20043.action）——两者格式不同，禁止用裸包名 com.hw.codearts... "。

**落点**：
- `src/providers/codeartsbuild/template-assembler.ts`（`validateSteps` 错误信息增强）
- `skills/codeartsbuild/SKILL.md`（规约补 module_id 格式说明）

### 2.4 P2：update_job 字段契约确认（已生效，无需改）

**现状**：[973] update_job 后 command 空——但 update_job 已调 `assembleConfig`（含 `validateStepProperties` + `validateStepImage`），FE-16 §2.1 字段契约对 update_job **已生效**。

**根因分析**：
- update_job 调 `assembleConfig({ ...body, projectId })` → 内部 `validateSteps` 校验 steps 字段名
- [973] 的 command 丢失不在校验阶段——模型组装 body 时漏传/传错字段（如把 command 放错位置）
- `validateStepProperties` 只校验键名在白名单内，不校验"必须含 command"——command 缺失时模板默认 `""`（shell-command）或 `mvn package`（maven-build），不会 E_PARAM

**设计**：
- **无需代码改动**——校验链已完整
- **SKILL 规约补 update_job 注意事项**：update_job body 必须含 steps[].properties.command（覆盖默认命令），否则服务端用模板默认命令（可能是 PyInstaller 打包而非 pytest）
- **可选增强**（评估，非必须）：`validateStepProperties` 加"command 必填检查"——shell-command 模板的 command 为空时警告（模板默认 `""` 即 echo nothing）

**落点**：`skills/codeartsbuild/SKILL.md`（update_job 注意事项）

### 2.5 P2：构建失败优先 update 而非 delete 重建

**现状**：4 次 delete_job(confirm=true) 重建，每次失败即删——违反规约 #10。模型倾向"删了重建"因为重建比 update 心智模型简单（不用 get_job 回读）。

**设计**（两层）：

1. **delete_job 加前置引导**：delete_job(confirm=true) 时，先检查同 jobId 是否可 update（通过 get_job 回读判断）——若可 update，next_actions 引导"优先 update_job 修复，而非 delete 重建"：
   - delete_job 返回 `need_confirmation` 时（confirm=false 缺省），next_actions 追加：`构建失败时优先 update_job 修复（先 get_job 取原配置，改 steps 后整体提交），而非 delete 重建——delete 会消耗配额且需重新组装`
   - confirm=true 执行删除前不再二次拦（避免阻断），但 next_actions 已在 need_confirmation 阶段引导

2. **SKILL 规约 #10 强化**：明确"构建失败 → 先 get_job 回读 → update_job 改 steps（不删重建）；只有任务结构错误（如 jobName 错/scms 错）才 delete 重建"。

**落点**：
- `src/providers/codeartsbuild/delete-job.ts`（need_confirmation next_actions 加 update 引导）
- `skills/codeartsbuild/SKILL.md`（规约 #10 强化）
