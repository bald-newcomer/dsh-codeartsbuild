## 0. 文档定位

将 `step-index.json` 中的参数可用值枚举（`select` 数组）迁移到 `step-templates.json`，让模型在 `stepsPlan` 覆写 `properties.image` 时有可用版本列表可参照，消除臆造版本号的根因。本文档做设计与影响面分析，实施由用户确认后落地。

---

## 1. 问题背景

### 1.1 会话轨迹暴露的缺陷

`docs/example/session.jsonl` 记录了一次真实会话（dsh-quant 仓库创建构建任务）：

| # | 模型行为 | 问题 |
|---|---------|------|
| 1 | 识别项目为 TS/Node.js，需 node >= 20 | 正确 |
| 2 | get_job 回读已有任务，看到 `nodejs12.7.0` 镜像 | 信息收集 |
| 3 | **臆造** `nodejs16.13.0` 镜像版本填入 stepsPlan | ❌ 不在可用列表 |
| 4 | 服务端报 `x86-64架构中，镜像nodejs16.13.0不存在` | 失败 |
| 5 | 退回 `nodejs12.7.0`（模板默认）→ 不满足 node >= 20 | 受限 |
| 6 | 最终改用 npm-build 模板默认值绕开版本选择 | 绕过，未真正解决 |

### 1.2 根因：可用版本列表不可达

| 资产 | 内容 | 模型可见性 |
|------|------|-----------|
| `step-templates.json` | 14 个模板的 `template_id`/`module_id`/`properties`（仅默认值，**无可用值枚举**） | ✅ 经 SKILL references/step-templates.md 可见 |
| `step-index.json` | 20 个插件的白名单索引 + 参数定义（含 `select` 可用值数组） | ❌ 仅供组装器白名单校验，模型不可见 |

模型在 `stepsPlan` 里写 `properties.image: "nodejs16.13.0"` 时，**无法知道可用版本列表**——`step-templates.json` 里只有默认值 `nodejs12.7.0`，可用版本枚举（`nodejs8.11.2` ~ `nodejs24`）锁在 `step-index.json` 里不对外暴露。

## 2. 设计方案

### 2.1 核心思路：select 枚举迁移到 step-templates.json

在 `step-templates.json` 的每个模板 `properties` 里，为有 `select` 的参数增加 `select` 字段（可用值数组）。`step-index.json` 保留白名单索引职责，但移除 `select` 数组（避免双源维护漂移）。

### 2.2 数据结构变更

**变更前**（step-templates.json，仅默认值）：
```json
{
  "template_id": "npm-build",
  "name": "Npm构建",
  "module_id": "devcloud2018.codeci_action_20014.action",
  "properties": {
    "image": "nodejs12.7.0",
    "command": "npm install && npm run build",
    "preCondition": "SUCCESS"
  }
}
```

**变更后**（step-templates.json，默认值 + 可用值枚举）：
```json
{
  "template_id": "npm-build",
  "name": "Npm构建",
  "module_id": "devcloud2018.codeci_action_20014.action",
  "properties": {
    "image": "nodejs12.7.0",
    "image_select": ["nodejs8.11.2", "nodejs10.1.0", "nodejs10.15.3", "nodejs12.7.0", "nodejs13", "nodejs14", "nodejs15", "nodejs16", "nodejs18", "nodejs20", "nodejs21", "nodejs22", "nodejs24"],
    "command": "npm install && npm run build",
    "preCondition": "SUCCESS"
  }
}
```

**命名约定**：`{param}_select` 后缀标识可用值枚举（如 `image_select`、`gradle_select`、`jdk_select`），与业务参数名 `{param}`（如 `image`、`gradle`）区分——组装器透传时只取 `{param}`，`{param}_select` 仅供模型参考，不进入请求体。

### 2.2.1 实施路径：改 generate-templates.py（脚本可重跑）

`step-templates.json` 由 `docs/example/generate-templates.py` 从 `step-index.json` 生成（FE-04 §7.2）。当前脚本只取 `default_properties` + `parameters[].default`，未携带 `parameters[].select`——这是 select 丢失的根因。

**实施路径**：改 `generate-templates.py`，让生成脚本从 `step-index.json` 的 `parameters[].select` 读取并写入 `step-templates.json` 的 `{param}_select`，保持"脚本生成"链路完整、可重跑刷新。

**generate-templates.py 改动要点**：
1. 读取 `step-index.json` 时，为每个模板建立 `parameters[].select` 的 param_name → select 数组映射
2. 写入 `step-templates.json` 的 `properties` 时，对每个有 `select` 的参数，追加 `"{param}_select": [...]` 字段
3. 重跑脚本 → `step-templates.json` 自动携带 `{param}_select`

**生成链路（改动后）**：
```
step-index.json (parameters[].select)
  → generate-templates.py（新增：param select → {param}_select 映射）
  → step-templates.json (properties.{param}_select)
```

**重跑刷新**：服务端插件/镜像版本更新后，重跑 `extract-step-index.py` 刷新 `step-index.json` → 重跑 `generate-templates.py` 刷新 `step-templates.json`，`{param}_select` 自动同步。

### 2.3 组装器适配（template-assembler.ts）

`assembleSteps` 当前逻辑（template-assembler.ts:160-172）：取模板 `properties` → 合并 `stepsPlan[].properties` 覆盖 → 返回。

**变更**：组装时**剥离 `_select` 后缀字段**（不进入请求体）：

```typescript
// assembleSteps 内，合并 properties 后剥离 _select 字段
const merged = { ...tpl.properties, ...(plan.properties ?? {}) };
// 剥离 _select 后缀字段（仅模型参考，不进请求体）
for (const k of Object.keys(merged)) {
  if (k.endsWith('_select')) delete merged[k];
}
return { module_id: tpl.module_id, name: tpl.name, properties: merged, enable: true };
```

**`assembleConfig` 的显式 steps 分支**（template-assembler.ts:201）：同样剥离——显式 steps 原样透传，但若用户/模型从模板复制了 `_select` 字段进来也需剥离。

### 2.4 step-index.json 变更

- **保留** `parameters[].select` 数组（双源交叉校验——与 step-templates.json 的 `{param}_select` 作一致性断言）
- **保留** `parameters[].name`/`label`/`required`/`default`（参数元信息，白名单校验仍需）
- **保留** `default_properties`（与 step-templates.json 的 properties 默认值对齐，作交叉校验）
- **不变**：step-index.json 本身不改动（select 保留原位，`generate-templates.py` 从它读取写入 step-templates.json）

### 2.5 references/step-templates.md 同步

在模板清单表里为有 `select` 的参数补"可用值"列（或附注），让模型在 SKILL 上下文直接看到可用版本。示例：

| template_id | 关键默认 properties | 可用值枚举 |
|-------------|---------------------|-----------|
| `npm-build` | image=nodejs12.7.0, command | image_select: nodejs8.11.2 ~ nodejs24 |
| `maven-build` | image=maven3.5.3-jdk8-open | image_select: maven3.5.3-jdk8-open ~ maven3.9.9-jdk21 |

## 4. 决策确认（2026-10-09）

| 决策点 | 选择 | 说明 |
|--------|------|------|
| select 存放方式 | **`{param}_select` 后缀** | 平铺在 properties 里，模板自包含，组装器剥离 `_select` 后缀键 |
| step-index.json select | **保留（双源交叉校验）** | step-index.json 不移除 select，与 step-templates.json 的 `{param}_select` 作交叉校验（可加一致性断言） |
| 6 个多余条目 | **不迁移** | 只迁移 step-templates.json 中 14 个模板的 select；step-index.json 多余 6 个条目的 select 保留不动（不在模型可见模板里，无臆造风险） |

## 6. 延伸修复（2026-10-10，c6ca1e11 完整会话复盘并入）

`docs/example/dsh-session-session-c6ca1e11-... (1).zip`（同一会话完整版，89 步/92 工具调用）暴露 `_select` 迁移之外的三个问题，一并并入本文档落地：

### 6.1 A：image 可用值白名单校验（机制层拦截臆造镜像）

**会话证据**：模型臆造 `nodejs18.0.0`/`nodejs14.17.0`/`nodejs20.0.0`/`nodejs24.0.0` 逐一尝试，全部"镜像不存在"→ **6 轮构建空转**（buildNo 3/4/6 均 SCHEDULE_FAILURE）。`_select` 枚举虽已迁移但仅"模型可见"——模型仍可能不参照硬猜。

**修复**（template-assembler.ts）：`validateStepImage`——steps/stepsPlan 组装后校验 `properties.image`：
- 模板有 `image_select` → image 必须在枚举内（默认值放行）
- 模板无 `image_select` → 覆盖 image 一律 E_PARAM（默认值放行，如 upload-release 默认 shell 镜像）
- 错误信息列出可用镜像，引导用默认值或改用有枚举的模板

**落点**：`assembleSteps`（stepsPlan 分支）组装期校验 + `validateSteps`（显式 steps 校验）。新增用例 6（template-assembler）+ 3（create-job）。

### 6.2 B：wait_build vs get_status 状态口径矛盾（completed 一律复核 record-info）

**会话证据**：buildNo 5 / 新任务 buildNo 1，`wait_build` 返回 **SUCCESS**（ShowJobStepStatus workflow.completed 无 error）但 `get_status` 返回 **FAILURE**（ShowJobBuildRecordDetail result.status=FAILED）——模型困惑于两工具口径矛盾，多次 get_log 复核。

**根因**：`mapStatusWithVerify` 只在 `completed + error` 时复核 record-info；`completed` 无 error 时直接按 workflow 判 SUCCESS，未复核权威数据源。

**修复**（wait-build.ts）：`rawStatus === 'completed'` **一律复核 record-info**（双数据源不同步，record-info 为权威——契约 §4.1 实调结论），消除 wait_build=SUCCESS 而实为 FAILED 的口径矛盾。更新 2 个既有用例断言（调用次数 +1）。

### 6.3 C：update_job body 传参退化（错误信息引导 + handler 严格校验）

**会话证据**：长会话尾部（step 85/87）模型把 `body` 传成字符串 / 缺 `jobId` → `invalid arguments: "body" must be an object` / `missing required property "jobId"`——模型在长上下文尾部开始胡乱传参。

**修复**：
- `parameters.ts` updateJobParameters：body 描述强化（"先 get_job 取原配置，全量覆盖，禁止手拼残缺 body"）；jobId 描述补来源
- `update-job.ts` handler：body 严格校验（object 非空非数组）+ jobId 错误信息引导"先 get_job"
